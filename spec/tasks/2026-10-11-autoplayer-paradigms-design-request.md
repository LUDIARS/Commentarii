> オートプレイヤー作る。

## 追加指示 (neco 2026-10-11): Commentarii から切り離して運用する

オートプレイヤーは独立したプロジェクト (別リポ) とする前提で設計する。設計書は Commentarii の spec/plan に置いてよい。次を節として必ず含める。

1. Commentarii に残すもの (攻略本ツクール・攻略本バンドルのスキーマ・validate・render・意図ズレ検証など) と、オートプレイヤー側へ移すもの (判断エンジン・アダプタ契約と SDK・sim・リプレイ・bench など) の境界案。
2. 両者をつなぐ契約 (攻略本バンドル / ルールブックの読み込み形式、観測・リプレイ・判断ログの受け渡し、版の対応)。
3. 既存の Commentarii 実装 (`src/engine`, `src/adapter*`, `src/replay`, `src/bench`, `src/gate` など) の移し方と、移行中の互換。
4. 新リポの名前候補 (LUDIARS の命名はラテン語。推奨つき)。

## 設計してほしいこと

叩き台 §16 をそのまま認めず、独立に考えて設計書を書く。叩き台と違う結論になってよい。特に次を必ず扱う。

1. **「判断系アルゴリズムを理解している」の意味と構成**: 5 方式 (BT / FSM / Utility / GOAP / MCTS) をどう持ち、どう組み合わせ、局面ごとにどう選ぶか (方式選択器の入力・規則・学習)。層構造にするか、並列に競わせるか、別の形か。相手 (敵 AI) のモデルとしての 5 方式の扱い。
2. **ルール / メカニクスのデータ表現**: 前向きモデル (シミュレーション) が組めるだけの表現力と、人間が書ける・マスターデータから取り込める簡潔さの両立。リアルタイム・連続空間 (Bestia) とターン制・離散 (KonbiniDominant / カード系) の両方に効く形。移動・空間・時間・確率・クールダウン・資源・相手の挙動。式言語の拡張範囲。
3. **「攻略法に依存せず、能力的にできることを判断・解釈する」**: 定石 (`tactics/`) を判断の入力にしないとき、何から計画を作るか。アフォーダンス (今できる / 数手でできる / 試さないと分からない) の定義、効果が分からない能力の実験と効果の学習、自分で見つけた手を定石として書き出す経路。
4. **マスク原則との整合**: `player` モードで masked のルールが前向きモデルに入らないことの構造的担保。「存在も知らない仕組み」と「存在は知っているが値が分からない仕組み」の区別。学習で推定した効果の knowledge。
5. **性能と決定性**: リアルタイム (毎ティックの時間予算) での GOAP / MCTS の予算と打ち切り、計画の使い回し、seed による決定性 (既存のリプレイ検証 `guide replay play` が通ること)。
6. **既存資産との関係**: 段 3 の `utility-bt` エンジン、§8.2 の定石書き換え、§8.5 の行動可能性、§14.C バランス回帰ゲート (基準値は既存エンジンで取ってある)、§14.E ペルソナ、§14.F 敵 AI への再利用。何を残し、何を置き換えるか。
7. **実装の分割と受入条件**: MVP で縮めないフルセットの段分け (叩き台は R1 ルールブック → R2 判断方式 5 種 → R3 方式選択と自律構え)。段ごとに機械判定できる受入条件 (テストで何を示すか)。
8. **叩き台 §16 の誤り・抜け・過剰** を具体的に列挙する。
